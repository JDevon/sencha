Sencha

A network package built around GreenTea. Includes strictly typed remotes and replicators.

Full API reference at jdevon.github.io/sencha.

Core features​

  • One shared module: defines a feature's remotes and replicators for both the server and the client.
  • Typed remotes: events, unreliable events, functions and switchboards, with arguments and return values checked on both sides.
  • Built-in protection: per-player rate limits and type checks on every call from a client, with warnings that can't flood your output.
  • Server-owned state: saved and temporary replicators that send server values to one player or the whole server.
  • Saved data without lock-in: replicate parts of a player's save file from any data store, with the save data fully typed.
  • Incremental updates: send small patches instead of whole values.
  • Client prediction: predict the result of server requests
  • React ready: getObservable works with the ReactObservableValue hooks.

Install​

Install with Wally by adding Sencha and GreenTea to your wally.toml:

[dependencies]
Sencha = "jdevon/sencha@0.2.0"
GreenTea = "corecii/greentea@0.4.11"

Usage​

Define a feature's remotes and replicators in one module that the server and the client both require:

-- ReplicatedStorage/CurrencyNetwork.luau
local Sencha = require(ReplicatedStorage.Packages.Sencha)
local gt = require(ReplicatedStorage.Packages.GreenTea)

return Sencha.define(script, {
    -- remotes
    buyItemRemote = Sencha.func(gt.args(gt.string()), gt.returns(gt.boolean())),

    -- replicators
    coinsReplicator = Sencha.temporaryReplicator.player(gt.number(), 0),
    shopDiscountReplicator = Sencha.temporaryReplicator.global(gt.number(), 0), -- a store-wide sale every player sees
})

Every Sencha implementation gets its name from its key in Sencha.define, so the same module resolves to the same remotes and replicators on both sides.

-- server
CurrencyNetwork.buyItemRemote:onServerInvoke(function(player, itemId)
    return CurrencyNetwork.coinsReplicator:tryUpdate(player, function(coins)
        if coins < 10 then
            return false
        end
        return true, coins - 10
    end)
end)

-- client
Sencha.waitForReplicators() -- once, while loading

print(CurrencyNetwork.coinsReplicator:get())
CurrencyNetwork.coinsReplicator:onChanged(function(_player, newCoins, oldCoins)
    print(`coins went from {oldCoins} to {newCoins}`)
end)
local bought = CurrencyNetwork.buyItemRemote:invokeServer("sword")

Use remotes for requests and one-off events. Use a replicator for state the client should always have a current copy of.

Remotes​

ConstructorUse
Sencha.event(...types)a RemoteEvent with checked arguments
Sencha.unreliableEvent(...types)same as above, sent through an UnreliableRemoteEvent
Sencha.func(gt.args(...), gt.returns(...))a RemoteFunction with checked arguments and return values
Sencha.eventSwitchboard(...types)one RemoteEvent that routes client calls by port name
Sencha.funcSwitchboard(gt.args(...), gt.returns(...))one RemoteFunction that routes client calls by port name

Unreliable events may drop messages or deliver them out of order, with payloads limited to roughly 900 bytes.

Reliable remotes also have predicted versions of their client calls, fireServerPredicted and invokeServerPredicted. See Client prediction.

Rate limits and rejected calls​

The server checks calls from clients in this order: port (switchboards), rate limit, then argument types. A call that fails any of them is rejected:

  • Events drop the call.
  • Functions error back to the waiting client.
  • The server warns once per player, remote and reason, then stays quiet for that combination for 60 seconds, so a flood of bad calls can't bury real errors.

Every remote allows 60 calls at once and 30 per second per player by default. Change it where the remote is defined:

sellItemRemote = Sencha.event(gt.string(), gt.number()):rateLimit({ burst = 10, perSecond = 4 }),

Switchboards keep a separate budget for each port, so unrelated actions don't share one.

Calls your own code makes (fireServer, invokeServer, fireClient, and return values) error on bad types, since those are mistakes in your code.

Replicators​

Three kinds. All are owned by the server: clients can never write to them.

A player's data is only ever sent to that player. State other players need to see goes through a global replicator, so the server always chooses what becomes public.

onUpdateReceivedclientfires for each patch received (see Incremental updates)
predictionclientbuilds a prediction for this replicator (see Client prediction)
getConfirmed / onConfirmedChangedclientuse the server's value, without predictions

On the client, get, getAsync, observe, onChanged and getObservable include any pending predictions. Without predictions, they're the server's value.

On the server, player replicators take the player as their first argument (get(player), set(player, value)), and onChanged passes the player first on both sides.

  • Every listener method returns a function that disconnects it. It's safe to call twice, works as a task for any cleanup library, and can be returned straight from a React effect.
  • On the server, a change is sent to clients before onChanged fires, so anything a listener changes in response reaches clients after the change that caused it.
  • set errors at the caller if the value doesn't match the replicator's type. Setting a primitive to the value it already has does nothing. Tables always count as a change.
  • tryUpdate can't yield. Its function runs without yielding, so nothing else can change the value between reading and setting it. A yield errors.
  • Values are frozen on both sides.

Saved replicators​

A saved replicator is a read-only view of part of a player's saved data. To change it, update the saved data, and the change replicates. This keeps one way to write, so an update to several fields at once stays atomic.

Saved replicators come from a saved source, one per store of saved player data (your DataStore wrapper of choice, a web service, etc.). Create each source in a shared module with a unique name and the store's built GreenTea type:

-- ReplicatedStorage/PlayerDataSource.luau
return Sencha.savedSource("PlayerData", PlayerDataTypes.PlayerData)

-- in a network module
moneyReplicator = PlayerDataSource:replicator(gt.number({ integer = true, range = "[0, ]" }), function(playerData)
    return playerData.money
end),

The saved data passed to the lookup is fully typed from the source's GreenTea type, so a misspelled field is a type error. GreenTea types can also set limits: here money must be a whole number of 0 or more ("[0, ]" leaves the maximum open), and a value outside that is caught on the server instead of being sent.

On the server, connect each source to its store. Sencha doesn't depend on any specific data store library:

-- a fetch function that yields until the player's data has loaded, or returns nil if it never loads
PlayerDataSource:setFetchFunction(function(player)
    local didLoad, playerData = PlayerDataServer.waitForPlayerData(player)
    return if didLoad then playerData else nil
end)

-- in the store's change callback, including the first load (oldData is nil)
PlayerDataSource:replicateChanges(player, newData, oldData)

Changes are found by comparing what each lookup returns, so a lookup must return an existing table from the saved data, or a primitive. A lookup that builds a new table counts as changed on every save. Data stores that keep unchanged tables as the same table (like Lyra) only send what changed. Be wary of data stores that deep copy the whole save on every change: every table becomes new, so every replicator that returns a table resends its full value and fires onChanged on every save, even when its part didn't change.

Incremental updates​

By default every change sends the whole value. For large values that change a little at a time, a replicator can send patches instead, by passing an incremental config as its last argument:

-- shared: a backpack maps item ids to counts, and a patch has the new count of each item that changed (0 removes it)
InventoryTypes.Items = gt.build(gt.dictionary(gt.string(), gt.number()))

function InventoryUtil.applyItemsPatch(items, patch)
    local newItems = table.clone(items)
    for itemId, count in patch do
        newItems[itemId] = if count > 0 then count else nil
    end
    return newItems
end

function InventoryUtil.diffItems(newItems, oldItems)
    local patch = {}
    for itemId, count in newItems do
        if oldItems[itemId] ~= count then
            patch[itemId] = count
        end
    end
    for itemId in oldItems do
        if newItems[itemId] == nil then
            patch[itemId] = 0
        end
    end
    return patch
end

-- temporary: a backpack that only lasts one round. The server sends patches with applyIncrementalUpdate
roundBackpackReplicator = Sencha.temporaryReplicator.player(InventoryTypes.Items, {}, {
    patchType = InventoryTypes.Items,
    apply = InventoryUtil.applyItemsPatch,
}),

-- then on the server, only the changed item is sent, not the whole backpack
BackpackNetwork.roundBackpackReplicator:applyIncrementalUpdate(player, { sword = 2 })

-- saved: the backpack in the player's save file. The server works out each patch itself with diff
backpackReplicator = PlayerDataSource:replicator(InventoryTypes.Items, function(playerData)
    return playerData.backpack
end, {
    patchType = InventoryTypes.Items,
    diff = InventoryUtil.diffItems,
    apply = InventoryUtil.applyItemsPatch,
}),
  • apply runs on the server and the client, so both always hold the same value. It must return a new table and never edit its input, since values are frozen.
  • For saved replicators, apply(old, diff(new, old)) must equal new.
  • Players who join, and replicators defined later, always get a full value first.
  • After the first value, an incremental replicator only sends patches, unless a temporary replicator's set sends a whole value.
  • A patch failing on the client means a bug, like an apply that gives different results on each side. It errors in Studio and warns in live games, and the client ignores that replicator's patches until the server sends a whole value. The server also checks that each saved replicator's apply matches its diff: in Studio a mismatch errors, and in live games it warns once per replicator.
  • onUpdateReceived only fires for patches. Use onChanged to see every change.

Client prediction​

A predicted remote call shows its result on the client straight away, instead of after a round trip to the server. Once the server has handled the call, its value replaces the prediction in a single step. A correct prediction never flickers or counts twice.

local bought = ShopNetwork.buyItemRemote:invokeServerPredicted({
    CurrencyNetwork.coinsReplicator:prediction(function(coins)
        return coins - price
    end),
    BackpackNetwork.backpackReplicator:prediction({ sword = 1 }), -- a patch, on an incremental replicator
}, "sword")
  • Build predictions with a replicator's prediction method. It takes either a function that returns the predicted value, or a patch for a replicator with an incremental config. It checks the prediction against that replicator's types.
  • Send them with a predicted call. Events and event switchboards use fireServerPredicted. Functions and function switchboards use invokeServerPredicted. Unreliable events can't be predicted because a dropped message would never be confirmed.
  • One call can predict several replicators, like coins and a backpack. They're confirmed together.

What each method shows​

MethodWhile a prediction is pending
get, getAsync, observe, onChanged, getObservablethe predicted value
getConfirmed, onConfirmedChangedthe server's value
onUpdateReceivedonly the server's patches

UI built on observe, onChanged or the ReactObservableValue hooks shows predictions without any changes. A correct prediction fires onChanged once, when it's made. A wrong one fires it again when it's rolled back to the server's value. Use onConfirmedChanged for callbacks that should only run for confirmed changes.

How it stays exact​

While a player's predicted call is being handled, the server holds back that player's replicator updates. It sends them together with the call's confirmation. The client then applies the server's changes and removes the prediction at the same time. This has a few consequences:

  • A predicted call's handler must make all of its replicator changes before it returns. Yielding inside the handler is fine. Changes from other threads are fine too, as long as they happen before it returns. A change made later (for example in a task.delay) arrives after the prediction was removed. The value then briefly shows the server's old value.
  • A player's predicted calls are handled one at a time, in the order they arrive. Normal calls aren't affected.
  • A player's other updates wait while their predicted call is handled. That's usually a few milliseconds. If a handler takes more than 2 seconds, Sencha stops waiting and removes the prediction. In Studio it also errors.
  • A prediction the server never confirms (for example after a lost connection) is removed after 10 seconds.

When not to predict​

  • The server would refuse the request. A prediction the server won't accept shows briefly, then rolls back. Check what you can on the client first, such as whether there's room. Skip the prediction (or the request) when it would fail.
  • Values the server changes over time, like regeneration or a countdown. Don't predict them. Replicate a start time and a rate instead, and work out the current value on the client.

React​

Use getObservable with ReactObservableValue:

local function CoinsLabel()
    local coins = ReactObservableValue.useObservableValue(CurrencyNetwork.coinsReplicator:getObservable())
    return React.createElement("TextLabel", { Text = `{coins} coins` })
end

Patterns​

Player replicators hold a separate value for each player, so they can send different data to different players. These patterns build on that, with no extra features needed.

Sending to a group of players​

To send the same value to a group, like a party, set it for each member. Every member's value can be the same frozen table, so this costs no extra memory:

-- shared
partyReplicator = Sencha.temporaryReplicator.player(PartyTypes.PartyState, PartyTypes.NO_PARTY),

-- server
local function syncParty(party)
    for _, member in party.members do
        PartyNetwork.partyReplicator:set(member, party.state)
    end
end

local function onJoin(party, player)
    table.insert(party.members, player)
    syncParty(party)
end

local function onLeave(party, player)
    table.remove(party.members, table.find(party.members, player))
    PartyNetwork.partyReplicator:set(player, PartyTypes.NO_PARTY)
    syncParty(party)
end

Groups can be created and removed at any time. Keep every change to a group going through one function like syncParty, so no member is missed.

For large group values, send only what changed: give the replicator an incremental config, send each new member the full value once with set, then send every change to all members with applyIncrementalUpdate. See Interest management for an example of patches sent to individual players.

Interest management​

To send each player only part of a large table, like the mobs near them, give each player their own view of the table and update it with patches. The game keeps the full table and decides what each player can see:

-- shared
MobTypes.MobState = gt.build(gt.table({ kind = gt.string(), health = gt.number() }))
MobTypes.MobMap = gt.build(gt.dictionary(gt.string(), MobTypes.MobState:type()))
-- a mob's new state, or false to remove it
MobTypes.MobPatch = gt.build(gt.dictionary(gt.string(), gt.union(MobTypes.MobState:type(), gt.literal(false))))

function MobTypes.applyPatch(mobs, patch)
    local newMobs = table.clone(mobs)
    for mobId, mobState in patch do
        newMobs[mobId] = if mobState == false then nil else mobState
    end
    return newMobs
end

visibleMobsReplicator = Sencha.temporaryReplicator.player(MobTypes.MobMap, {}, {
    patchType = MobTypes.MobPatch,
    apply = MobTypes.applyPatch,
}),

Each player's value in the replicator is exactly the set of mobs they can see, so the server reads it with get(player) instead of keeping its own record:

-- server
local mobs: { [string]: { state: MobState, model: Model } } = {} -- the full table, kept by the game

-- run for each player periodically: adds mobs that came into range and removes ones that left
local function updateVisibility(player: Player)
    local visible = MobNetwork.visibleMobsReplicator:get(player)
    local patch = {}
    for mobId, mob in mobs do
        local inRange = isInRange(player, mob)
        if inRange and not visible[mobId] then
            patch[mobId] = mob.state
        elseif not inRange and visible[mobId] then
            patch[mobId] = false
        end
    end
    MobNetwork.visibleMobsReplicator:applyIncrementalUpdate(player, patch) -- an empty patch does nothing
end

-- sends a change only to the players who can see that mob
local function sendToViewers(mobId: string, value: MobState | false)
    for _, player in Players:GetPlayers() do
        if MobNetwork.visibleMobsReplicator:get(player)[mobId] then
            MobNetwork.visibleMobsReplicator:applyIncrementalUpdate(player, { [mobId] = value })
        end
    end
end

The client renders the first value once, then handles each patch as it arrives. Every change after the first value is a patch that says exactly what changed:

-- client
local visibleMobsReplicator = MobNetwork.visibleMobsReplicator

for mobId, mobState in visibleMobsReplicator:get() do
    MobVisuals.spawn(mobId, mobState)
end

visibleMobsReplicator:onUpdateReceived(function(_mobs, oldMobs, patch)
    for mobId, mobState in patch do
        if mobState == false then
            MobVisuals.remove(mobId)
        elseif oldMobs[mobId] then
            MobVisuals.update(mobId, mobState)
        else
            MobVisuals.spawn(mobId, mobState)
        end
    end
end)
  • Avoid set on this replicator. set sends a whole value, which onUpdateReceived doesn't see, so the client's visuals would fall out of step with its value. Send every change, including clearing a player's view, as a patch.

Rules​

  1. The server must require every module that defines replicators. A replicator only exists once its module has been required on the server.
  2. Call Sencha.waitForReplicators() on the client before starting systems that read replicated values, or use getAsync / observe in code that may run earlier.
  3. get doesn't yield, getAsync does.
  4. Remotes can't send every table. Use string keys for dictionaries, and avoid arrays with gaps, mixed array and string keys, and non-string keys. The server warns when a replicator's type can't be sent intact. In Studio it also checks each value it sends, since some problems (such as an array with gaps) only show up in replicated values.
  5. Avoid putting Instances in replicated values. With StreamingEnabled, an Instance the client hasn't streamed in arrives as nil. Send an InstanceHandle instead. The server warns about replicator types that contain Instances.
  6. Don't yield in a saved replicator's lookup, or in an incremental config's apply or diff (saved, temporary). A yield errors with a traceback to the line that waited.
  7. A predicted call's handler must make all of its replicator changes before it returns. See How it stays exact.
